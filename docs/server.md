# Server limits

Measured with `experiments/probe_bot` on 2026-11-03 unless noted.

## Scoring and maps

- The team's score is its best single server game played to the end, and practice games count. A kick or crash voids that game.
- **Each game re-rolls the map.** Every seed seen was different, and the biome changes within one upload. So there's no fixed map to solve.
- All 22 seeds seen are version 4 UUIDs. The bot never sees the seed during a game.
- Server games replay identically on the local engine, for frame position, score and dinosaurs.

The default C++ build keeps the x86-64-v3 ISA without CPU-specific tuning.
`--server-tune` opts only the `--linux` bot library into Cascade Lake scheduling;
local simulator tools remain untuned.
For local profile training and the profile-use server library, see
[Linux PGO builds](architecture.md#linux-pgo-builds).

## Server build preparation

**Important for agents: use `--server-tune` when preparing `search_bot` for
server games.** This is a build-time setting; the bot does not enable it
automatically when it connects to the server.

Use a current profile generated by `tools/build_pgo.py`, whose default merge
excludes `ValueNet`. If the profile is missing or stale, regenerate it using the
[PGO workflow](architecture.md#linux-pgo-builds), then build and package:

```bash
.venv/bin/python tools/build_sim.py --linux --only libsim --server-tune \
  --pgo-use build/pgo-untuned/sim.profdata
.venv/bin/python tools/make_zip.py bots/search_bot
```

The profile path above is the existing local experiment's output, not a tracked
file; substitute the current profile on your machine. Keep x86-64-v3 and leave
`ValueNet` excluded. Do not substitute plain `-mtune=cascadelake`, which Zig
interprets as a CPU selection and can enable AVX-512.

**Make this the last library build before packaging.** Ordinary local builds
replace `bots/search_bot/libsim.so` and can remove server tuning or PGO. Omit
`--server-tune` for local games. The flag is the intended server preparation
setting, but its performance on the server has not yet been measured. Preparing
an archive does not authorize running a server game.

## Timing

- **Tick limit: 150 ms.** A stall of 145 ms was on time and 170 ms was late.
- **The bot uses 95 ms** for search, set by `TIME_BUDGET_MS` in `bots/search_bot/bot.py`.
- Spikes hit even a trivial bot on the server: 8-14 ticks per game took 20 ms or more, and the worst took 49-65 ms. We haven't measured spikes on a local machine.
- With 95 ms the slowest moves reached 131-145 ms, and the bot lost about one tick per game.
- A late reply only loses that tick's action. 50 late ticks gets the bot kicked.
- Ticks 1-10 get an extra 1,000 ms.
- `sim_live` budgets in simulated ticks, not time, so its tests never include late ticks.

The 95 ms is a safety margin and not a tuned value. Going to 120 ms would add about 25% more search, worth about 900 points at the measured slope, before counting extra late ticks.

## Startup

- A connection must send REGISTER within 5 s, or the server closes it and the game is lost.
- `application.py` connects, builds `Bot()`, and only then registers, so `Bot.__init__` must stay fast.
- `bot.py` is imported before connecting, so slow setup belongs at module level. 19-22 s of startup worked. The bound is the 120 s game-start wait, less about 4 s of container boot.
- Don't use `multiprocessing` at import time, because workers re-import `bot.py`.

## Etiquette

Run one server command at a time, never poll or loop, and space games out. Three games about 80 s apart caused no trouble. Rate limits are unknown.
